# Laptop run, 2026-10-03

`uv run python -m benchmarks.throughput --dsn postgresql://postgres:postgres@127.0.0.1:55434/ratchet`

## Machine

- Intel Core Ultra 7 255H (16 logical CPUs), 31 GB RAM, Windows 11 26100, Python 3.14.6.
- Postgres 18.6 (alpine image) in Docker Desktop on the same laptop, default settings, reached through the published
  port. Every round trip crosses the Docker Desktop network bridge, which is slow next to a Linux host. Read these as
  a floor, not as what a server does.
- Workers are four separate `python -m ratchet worker` processes, 64 concurrent workflows each, a pool of 10
  connections each.

## What is measured

- **drain**: 5,000 workflows of three no-op steps are started first, then the workers start. Time from worker start to
  the last workflow completed.
- **latency**: workers running, 200 workflows a second started on an open loop (arrivals follow the clock, not the
  previous response) for 20 seconds. Latency is `finished_at - created_at`, both from the database clock.
- **replay**: the CPU cost of replaying a history, which every wake of a long workflow pays. Pure Python, no database.

## Results

Before and after one change: switching off asyncpg's connection reset on release, loading the history in one
statement, writing the final status and clearing retry bookkeeping in one statement, and skipping the history load on a
workflow's first claim (fence 1 means nothing can have been recorded). Round trips for a three-step workflow went from
about 19 to 5. ADR 8 has the reasoning.

| run | load | before | after |
|---|---|---|---|
| drain | 5,000 x 3 steps, 4 workers x 64 | 15.1 s, 331 workflows/s, 993 steps/s | 5.6 s, 896 workflows/s, 2,689 steps/s |
| latency | 200/s for 20 s, 3 steps | p50 50 ms, p95 157 ms, p99 255 ms, max 400 ms | p50 22 ms, p95 100 ms, p99 203 ms, max 330 ms |

| replay | per wake | per recorded step |
|---|---|---|
| 100 steps | 0.11 ms | 1.1 us |
| 1,000 steps | 1.19 ms | 1.2 us |
| 10,000 steps | 13.3 ms | 1.3 us |

## Run-to-run spread

After the review fixes (stored payloads handed back, parked branches waiting for siblings, the idle worker clearing its
wake flag before querying), the same harness ran twice more:

| run | drain | latency |
|---|---|---|
| 1 | 1,137 workflows/s | p50 20 ms, p95 53 ms, p99 130 ms |
| 2 | 926 workflows/s | p50 27 ms, p95 92 ms, p99 192 ms |

So on this laptop two runs of the same code differ by about 20 percent. The README quotes the original "after" row,
which sits inside that range; read every number here with that spread in mind.

## What these numbers do not say

- Nothing about a Linux host or a managed Postgres. The `bench` workflow in `.github/workflows/bench.yml` runs the same
  harness on a GitHub runner; its output goes in a file next to this one.
- Nothing about activities that do real work. The steps are no-ops, so this is the engine's own overhead.
- The latency tail (p99 around 200 ms) has not been profiled yet. The likely suspects are all four workers waking on
  every `NOTIFY` and racing for the same rows, and the Docker Desktop bridge.
